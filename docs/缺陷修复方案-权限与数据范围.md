## 二、P0-1 部门写操作数据范围校验（S1-1）

### 2.1 现状

- `UpdateDepartment`（L152）、`DeleteDepartment`（L204）、`GetDepartment`（L115）、`CreateDepartment`（L29）**完全没有**数据范围处理；

结论：基础设施齐全，只需把部门模块接入同一范式。

### 2.2 修复设计

**（1）Service 层：接口与实现增加 `op *EffectiveDataScope` 参数**

```go
// internal/service/department.go
type DepartmentServiceInterface interface {
    Create(ctx context.Context, op *EffectiveDataScope, req *CreateDepartmentRequest) (*DepartmentResponse, error)
    Update(ctx context.Context, op *EffectiveDataScope, id int, req *UpdateDepartmentRequest) error
    Delete(ctx context.Context, op *EffectiveDataScope, id int) error
    Get(ctx context.Context, op *EffectiveDataScope, id int) (*DepartmentResponse, error)
    Tree(ctx context.Context, req *ListDepartmentsRequest) ([]*DepartmentTreeNode, error)
    TreeInScope(ctx context.Context, op *EffectiveDataScope, req *ListDepartmentsRequest) ([]*DepartmentTreeNode, error)
    ChildIDs(ctx context.Context, id int, includeSelf bool) ([]int, error)
}
```

各方法在业务逻辑前插入校验（复用现有函数，fail-closed 语义已内建）：

```go
func (s *DepartmentService) Update(ctx context.Context, op *EffectiveDataScope, id int, req *UpdateDepartmentRequest) error {
    if err := ensureDepartmentInScope(op, id); err != nil {
        return err
    }
    // 移动部门时，新父部门也必须在范围内（防止把范围外部门"移入"自己范围后接管）
    if req.ParentID != nil && *req.ParentID > 0 {
        if err := ensureDepartmentInScope(op, *req.ParentID); err != nil {
            return err
        }
    }
    // ...原有事务逻辑不变
}
```

- `Delete`：`ensureDepartmentInScope(op, id)`；
- `Get`：`ensureDepartmentInScope(op, id)`；
- `Create`：`req.ParentID > 0` 时 `ensureDepartmentInScope(op, req.ParentID)`（顶级部门 ParentID=0 仅超管/All 可建：`isDepartmentInScope` 对 DepartmentID=0 已返回 false，天然满足）。

语义说明（与 `data_permission.go` 现有约定一致）：
- `op == nil`（内部调用）或 `IsSuperAdmin` → 放行；
- `DataScopeSelf` → 全部拒绝（实测中 self 账号也成功删除了部门，即本缺陷）；
- Department / DepartmentAndChild / Custom → 必须命中 `op.DepartmentIDs`；
- 未知 scope → 拒绝（fail-closed）。

## 三、P0-2 角色禁用后权限不失效（S1-2）

### 3.1 根因（三层叠加）

1. **中间件只信 Casbin**：`middleware/permission.go:54` `GetRolesForUserInDomain` → `Enforce`，g 规则未清则 p 规则按角色名继续命中；
2. **禁用不同步 g**：`service/role.go:441-480` `setStatus` 仅更新 DB status，未触碰 Casbin；
3. **缓存清理查错表**：`role.go:88-108` `clearUserPermissionsByRoleID` 仅遍历 `UserRole`（普通用户），**管理员绑定在 `AdminRole`**，管理员侧 `user:menu/button/api` 缓存直到 TTL 过期前一直返回旧权限 → 这也解释了"禁用后菜单反而全量展开"（菜单接口读缓存，角色变化后缓存未失效且聚合逻辑异常放大）。

### 3.2 修复设计（治本 + 防御纵深）

**（1）角色状态变更全量同步 Casbin g（治本）**

`service/role.go` 的 `setStatus` 在更新 DB 后增加 g 同步（伪代码）：

```go
// Disable：移除该角色在所有域中对全部持有者的 g 关联
// Enable：按 AdminRole/UserRole 现存绑定重建 g
func (s *RoleService) syncRoleGAssignments(ctx context.Context, r *ent.Role, active bool) error {
    enforcer, err := global.EnforcerManager.GetEnforcer("default")
    if err != nil {
        return err // 注意：现有代码普遍忽略此错误，此处必须上抛或重试，失败则回滚状态变更
    }
    // 收集 AdminRole + UserRole 持有者 UID
    uids := ... // SELECT uid FROM admin JOIN admin_role WHERE role_id=r.ID（含 UserRole 侧）
    for _, uid := range uids {
        if active {
            _, _ = enforcer.AddRoleForUserInDomain(uid, r.Name, "default")
        } else {
            _, _ = enforcer.DeleteRoleForUserInDomain(uid, r.Name, "default")
        }
    }
    return nil
}
```

要点：
- DB 状态更新与 g 同步放在同一事务边界外但需**失败补偿**：g 同步失败时回写状态（或先写 g 再改状态），禁止出现"DB 禁用、g 仍在"的中间态；
- Enable 时只对仍持有该角色的用户重建 g（AdminRole 表现存的）；
- 系统角色（admin/normal_admin）保持现有"不允许修改状态"的保护不变。

**（2）修复缓存清理的表错误**

`clearUserPermissionsByRoleID` 同时遍历两张绑定表：

```go
// 现状：仅 UserRole（漏管理员）

// 修复：增加
adminRoles, err := s.Client.AdminRole.Query().
    Where(adminrole.RoleIDEQ(roleID)).
    WithAdmin().
    All(ctx)
// 对 admin.Edges.Admin.UID 执行同样的 user:menu/button/api 缓存删除
```

同时 `setStatus`（L477）现有调用保留，并建议改用 `PermissionService.clearAllUsersPermissionsByRole`（`permission.go:482`）若其语义已覆盖两表（修复时核对）。

**（3）中间件防御纵深：enforce 前过滤非活跃角色**

不能只依赖 g 同步的完备性（多实例部署、历史脏数据、异常中断）。在 `middleware/permission.go`：

```go

// 新增：过滤 DB 中已禁用/已删除的角色名（带短 TTL 缓存，避免每请求查库）

// 任一 activeRoles 中的角色可命中 p 规则即放行（用 enforcer.HasPermissionForUserInDomain 逐角色判断）
```

实现要点：
- 新增进程内 `RoleStatusCache`（roleName → active，TTL 30~60s + 角色状态变更时主动失效）；

- **默认拒绝**：角色查不到（已删除）按禁用处理。

**（4）角色删除清理 Casbin（同时服务 S1-3）**

## 四、P1 角色替换后权限扩大（S1-3）

### 4.1 根因分析（含待执行的诊断）

实测：把用户 U 从角色 A 换绑为 test 后，`GET /user/permissions` 返回大量从未授予 U/A/test 的权限（含 `role:permissions:save`、`permission:add`），且 `GET /roles` 实际放行。定位路径：

1. **数据诊断（修复前先执行）**：

```sql
-- test 角色现有 p 规则（预期仅 cron-jobs 约 15 条）
SELECT v0, v2, v3, v4 FROM casbin_rule WHERE ptype='p' AND v0='test' AND v1='default';
-- U 的 g 关联（换绑后预期仅 test）
SELECT * FROM casbin_rule WHERE ptype='g' AND v0='<U.uid>';
-- 全表分布（找历史脏数据/孤儿规则）
SELECT ptype, v0, COUNT(*) FROM casbin_rule GROUP BY ptype, v0 ORDER BY 3 DESC;
```

2. **嫌疑点 A：覆盖式保存"保留范围外"策略**（`permission.go:1248-1276`）——非 `includeAll` 操作者保存时只删除其 scope 内旧规则、范围外旧规则保留。若历史上曾以低权限操作者或异常参数触发过部分删除/插入，将产生与 UI 展示不一致的规则集。UI（权限树）展示的是全量，保存却可能"合并不覆盖"。

3. **嫌疑点 B：AssignAdminRoles g 重建静默失败**（`role_assignment.go:368-378`）——`GetEnforcer` 出错或 `AddRoleForUserInDomain` 失败均被 `_, _ =` 吞掉，异常时新旧 g 并存或全失。

4. **嫌疑点 C：双数据源时序**——`/user/permissions` 直查 `casbin_rule` 表，而 middleware 用 enforcer 内存策略；`SaveRolePermissions` 虽有 Reload（测试 `ReloadsCasbinPolicy` 存在），但 g 变更路径（AssignAdminRoles）未见显式 Reload 依赖 adapter 自动同步，多实例下不一致。

### 4.2 修复设计

1. **g 维护错误处理**：`role_assignment.go` 两处 `_, _ =` 改为记录错误并**返回失败**（让事务语义完整：DB 已提交但 g 失败时，标记补偿任务或重试，绝不静默）；
2. **保存策略二选一并对齐 UI**：
   - 方案 a（推荐）：保存即全量覆盖（删除该角色 domain 下全部 p，再插入请求集），操作者越权的规则在 `getOperatorPermissionScope` 阶段已被 `allowsRule` 拒绝，无需"保留范围外"；
   - 方案 b：保留现有合并策略，但 `GetRolePermissions`/权限树接口必须返回**合并后的真实全量**，UI 勾选态与之对齐；
3. **统一权限判定数据源**：`/user/permissions` 聚合改为与 middleware 相同的 enforcer 查询（`GetImplicitPermissionsForUserInDomain`），消除表直查与内存策略的偏差；
4. **数据修复脚本**：按 4.1 诊断结果清理孤儿 p/g（可做成启动时一次性清理任务或手工 SQL，随版本发布）；
5. **一致性回归测试**：换绑角色后，立即断言 (a) `/user/permissions` 返回值 ⊆ 新角色权限并集；(b) enforcer.Enforce 对新旧权限分别放行/拒绝。
